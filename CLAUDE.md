# CLAUDE.md

Library of reusable GitHub Actions workflows (`workflow_call`) in `.github/workflows/`, consumed by every other repo under this account via `uses: dustfeather/shared-workflows/.github/workflows/<name>.yml@v10`. No app code. A merged change ships to every caller on next run — treat blast radius accordingly. Two workflows are NOT callable: this repo's own automation, `tag-release.yml` (cuts the version tag) and `guard-tests.yml` (runs the guard suites below, plus actionlint over every workflow). No workflow here reviews or merges PRs: review runs locally before the push, merges are by hand.

## Verifying changes

**Touching the pnpm-version guard — the `run:` block between the `# pnpm-guard-slice-begin` and `# pnpm-guard-slice-end` markers, shipped in `node-test.yml`, `deploy-cloudflare.yml` and `release-extension.yml` — run `bash tests/pnpm-guard/run.sh` before pushing.** Describe the region by the markers and nothing else: anchoring an extractor on a line of the code under test exempts that line from mutation (rewriting it deletes the anchor and the slice silently matches something further down), and `tests/pnpm-guard/extract.sh` refuses rather than guessing when they are absent. Two things are specific to this one. The block is duplicated across workflows, and the extractor **derives** the set rather than holding a list: every `.github/workflows/*.yml` carrying the markers, asserted equal to the set calling `pnpm/action-setup`, in both directions — a caller with no slice is a guard nobody tests, and a slice in a workflow that never calls the action is a guard that cannot fire. Never replace that with a hand-written list. A list is what lets someone add a fourth workflow by copying the pnpm block, set its `PNPM_BOOTSTRAP_VERSION` literal correctly so `check-workflows.py` passes, break the copied guard, and ship green — the extractor would never read the file. It then refuses unless the copies are **byte-identical**: the suite exercises one on behalf of all, so drift between them is a failure, not a diff. And the branch worth protecting is the warn path: it exits 0 on a value the workflow itself calls wrong, so an inverted `-z` or a typo that stops the guard firing is green in every caller until it reaches a pool exporting `pnpm_config_store_dir` — the same "first run passes, a later one dies" shape the guard exists to prevent. Assert the annotation alongside the exit status, never the status alone. The pre-push hook and the `guard` job both run it.

**Raising the pnpm pin is one commit, never two.** The `pnpm-version` default, the `pnpm/action-setup@<sha>` pin and that SHA's committed bootstrap lockfiles are a three-way agreement, and `scripts/check-workflows.py` asserts all three (the lockfile leg under `CHECK_PNPM_BOOTSTRAP=1`, which the hook and the `guard` job both set). An unreachable lockfile is a **hard** failure by default; `PNPM_BOOTSTRAP_SOFT=1` downgrades it to a note and **only the pre-push hook may set it**, so that an offline push is not blocked by a check that never disagreed. The switch is an opt-in to silence rather than an opt-in to strictness on purpose: it used to read ambient `CI`, which made the required check's strictness depend on a variable nothing declared, so a tidy-up of an `env:` block could turn it into a green no-op. `check-workflows.py` now asserts the `guard-tests.yml` step sets `CHECK_PNPM_BOOTSTRAP=1` and does **not** set `PNPM_BOOTSTRAP_SOFT`, reading the parsed `env:` maps rather than the file text — a text scan matches the comment explaining why the variable is absent, and "fix" it by deleting the explanation. The action never reads the runner image's pnpm: `runSelfInstaller()` wipes its dest dir, installs from its own committed lockfile and then runs `pnpm self-update <input>` unconditionally — so the default matters only in that it must equal what the pinned SHA bootstraps, which makes that self-update a no-op. Any other value installs pnpm THROUGH pnpm into the shared store and kills every job after the first. Move the SHA, the default and the `PNPM_BOOTSTRAP_VERSION` literal in all three guards together, in the same commit.

**Touching the cache-glob block — the `run:` block between the `# cachedeps-slice-begin` and `# cachedeps-slice-end` markers, shipped in `node-test.yml` and `deploy-cloudflare.yml` — run `bash tests/cachedeps/run.sh` before pushing.** Same marker discipline as the pnpm guard above, and `tests/cachedeps/extract.sh` refuses rather than guessing when the markers are absent. What makes this block worth a suite is that its output is `actions/setup-node`'s `cache-dependency-path`, and with `cache` set setup-node **fails the step** rather than skipping when nothing in that list resolves — on `deploy-cloudflare.yml` that is the deploy path, and a reusable workflow cannot be run from a local checkout, so extraction is the only way to exercise it before it reaches every caller. Two things are specific to it. The copies are NOT byte-identical — one reads `WORKING_DIR`, the other `INSTALL` — so the pnpm guard's identity assertion does not apply; instead every case runs against both slices and asserts they agree, which catches drift without demanding a sameness the files cannot have. Each slice is given **only its own** directory variable, read from the shipped `env:` block by `extract.sh --env-keys` — never both. Exporting both is what would make the copies agree on a mistake rather than catch it: the way a third copy gets made is by pasting an existing slice, and a pasted `${INSTALL:-.}` inside `node-test.yml` does not trip `set -u`, so it silently reads `.` for every `working-dir` and emits root-only globs. That reaches only callers whose lockfile sits under `working-dir` — the default shape stays green, which is the same "first run passes, a later one dies" pattern the pnpm guard exists for. The suite also refuses when a slice never references the variable its own workflow declares. And the set of copies is derived, not listed: the marked files are asserted equal to the files carrying an `id: cachedeps` step, anchored so that prose merely naming the id does not count (`guard-tests.yml` carries exactly that in a comment). Half the suite asserts an ABSENCE — no `*lock*` glob, nothing that `Cargo.lock` could satisfy — because the too-broad glob passes every shape assertion and still keys the node cache off a Rust file, and because a repo with only a `Cargo.lock` at the root would satisfy setup-node's lookup instead of failing loudly.

Everything else: the checks are a YAML parse (`python3 -c "import yaml; yaml.safe_load(...)"`) plus `scripts/check-workflows.py`, and `actionlint` over every workflow. `check-workflows.py` is no longer local-only — it runs in CI as a step of the `guard` job, which is the one required status check on `main`, so its findings now block a merge instead of only a push. Treat a new assertion in it as changing what that gate enforces fleet-wide, and give it a fixture case in `tests/check-workflows/run.py` rather than relying on the clean tree passing — that proves the happy path and nothing else, and a regex here has already shipped broken twice (one double-escaped and matched nothing, one matched prose instead of `uses:` lines, both green). The fixtures are offline: every case reaching the network stubs `fetch_json`, and the ones that do not stub it never set `CHECK_PNPM_BOOTSTRAP`, so no case can hit api.github.com by accident. The pre-push hook runs the contract checks, the pnpm-version guard suite, the cache-glob suite, the workflow-check fixtures and the lint as five independent checks, each probing for its own dependencies (PyYAML for the first, `python3` alone for the second and the third: both blocks under test are pure shell, but each `extract.sh` slices its block out with a python3 heredoc; PyYAML again for the fourth, and `actionlint` AND `shellcheck` for the fifth) and skipping only itself — a single missing dependency must not take the others down with it. The lint probes for `shellcheck` separately because actionlint drops every shell check when it cannot find that binary and still exits 0, so a clean run without it would mean nothing. **The same lint runs in CI as the last step of `guard-tests.yml`'s `guard` job** — which runs, in order, `tests/pnpm-guard/run.sh`, `tests/cachedeps/run.sh`, `tests/check-workflows/run.py`, `check-workflows.py` under `CHECK_PNPM_BOOTSTRAP=1`, then actionlint — deliberately that job rather than a new one, because `guard` is the one required status check on `main`, so a step there is enforced the moment it lands while a new job would gate nothing until branch protection is edited. CI pins actionlint by version and sha256; a local binary of another version shows up as a CI-only finding, and the fix is to bump the local binary, never to suppress the finding. A false positive is silenced with a scoped `# shellcheck disable=SCxxxx` comment carrying a one-line reason — the ones that ship today cover two shapes (literal `${NPM_TOKEN}` in an .npmrc line, and deliberate word splits such as one name per `printf` argument), and each is load-bearing: "fixing" it by quoting would break the thing it documents. Reusable workflows cannot be invoked from a local checkout — `uses:` resolves through GitHub. Real e2e test: push to feature branch, point one caller at it (`@feature/<name>`) before tagging.

## Versioning — pick bump by caller impact

`tag-release.yml` auto-tags every push to `main`: default bumps **patch** (wraps at 100 → minor; minor uncapped), re-points the floating major tag (currently `v9`). **major never bumped automatically.** Larger bump: put `#minor` or `#major` **in the PR title** when it lands through a PR, **on the commit subject** when pushed straight to `main` (largest wins). Match is fixed-string over the **subject** of **every commit in the push**, not just HEAD — one push fires one run, so a HEAD-only scan would drop a token from an earlier commit in a batch. Bodies are excluded on purpose: prose *discussing* a bump matched itself and cut a spurious minor. Don't write tokens verbatim unless you mean them — **in a PR title least of all**, since that text is now always the landing subject, so prose merely *naming* a token cuts that release. This is the same failure the body exclusion exists to stop, on the one channel where no exclusion is possible.

**PR title, by repo setting.** PRs land with a squash merge, done by hand (a rebase merge is replayed server-side and arrives unsigned; GitHub signs a squash commit with its web-flow key). The subject of the squash commit comes from the repo's `squash_merge_commit_title`, and GitHub's default `COMMIT_OR_PR_TITLE` uses **the single commit's own subject on a one-commit PR**, switching to the PR title only from two commits up, so a `#minor` typed only in the title of such a PR would be dropped silently and cut a patch. The repo is set to `PR_TITLE` (measured before and after: `gh api repos/dustfeather/shared-workflows --jq .squash_merge_commit_title`), so the title wins on every squash regardless of how many commits the PR has. `allow_rebase_merge` is `false` for the signing reason above. Both are asserted by `merge_settings_drift()` in `scripts/check-workflows.py` under `CHECK_MERGE_SETTINGS=1`, for the reason the rest of this file keeps reaching for: a setting that lives in no file is exactly what a comment asking the next reader to remember cannot hold. Two things about it are specific to reading SETTINGS rather than files, and both were measured on a throwaway branch (2026-09-22, two jobs in one run) rather than reasoned about.

**It reads nothing without `contents: write`, and the response will not tell you that.** With `permissions: contents: read` the three keys come back ABSENT; with `contents: write` they come back `PR_TITLE` / `false` / `true` — while `.permissions.push` is `false` in BOTH responses, so the object's own push flag does not predict its own field set. An unauthenticated GET of this public repo likewise answers 200 with none of the keys. So **absent is not false**: treating a missing key as a pass would make the check a green no-op the day the token scope changes, so it is reported as "could not check" and is hard by default. `MERGE_SETTINGS_SOFT=1` downgrades that to a note, and only the pre-push hook sets it — locally the read is usually unauthenticated, so the honest local verdict is "could not check".

**It therefore runs in its OWN job (`settings`), on `push` only, and is not the required check.** Permissions are a job property, so the leg could not sit on `guard` without either over-scoping the one required status check or reddening it on every run — caught in pre-push review rather than in CI, which is what that review is for. It could not gate a PR even with the scope: a `pull_request` run opened by `dependabot[bot]` gets a read-only token whatever the `permissions:` block says, so on the PR path the fields are unreadable by construction. What the job does is turn `main` red immediately after a merge — the run before the next release is cut — and the gate assertion is correspondingly **exactly-one and step-scoped**: at least one step in `guard-tests.yml` must carry `CHECK_MERGE_SETTINGS=1` in its OWN `env:`, so deleting the job is a finding, a second script step without it is fine, and setting the flag at workflow or job level is itself a finding. That last one is not pedantry: an inherited flag reaches every script step including the one in `guard`, which would satisfy a naive count while reddening the required check on every run — the failure this job exists to prevent, arriving through the assertion meant to protect it. The file being absent entirely is also its own finding rather than left to `pnpm_pin_drift`, which reports it today: borrowed coverage disappears when the lender is refactored. That is the opposite shape from `CHECK_PNPM_BOOTSTRAP`, which every script-running step must set, and the asymmetry is the measurement above, not a preference.

**Placement is only half of it: where the flag is written says nothing about whether it is ever run.** So every job that enables it is also asserted reachable and scoped — `permissions: contents: write` (anything less makes the three keys absent, so the leg could only ever report "could not check"), `if: github.event_name == 'push'` pinned exactly against `MERGE_SETTINGS_JOB_IF`, and an `on.push` mapping carrying no `paths`/`paths-ignore` filter and keeping main among its branches. The exact condition is deliberate ceremony: changing WHEN the settings are read should cost an edit here, in the constant and in the fixtures, not one line in a workflow. The permission leg is also what catches the case the separate job exists for, which the placement rule alone does not — moving `CHECK_MERGE_SETTINGS` into the required `guard` job's OWN step `env:` satisfies an exactly-one count, because only workflow- and job-level placement is rejected. Of the three edits this closes, two turn `main` red on every push and one is silent: a `paths:` filter, which reads as a harmless tidy-up, quietly stops the job being reached on the merges that matter. Each was verified by mutating the shipped `guard-tests.yml` — scope, condition, filter — and not only by fixtures.

- **patch** — bug fix, doc/log/comment tweak, internal refactor, bumping action used inside workflow with no interface change.
- **minor** — backwards-compatible feature: new *optional* input (with default), new workflow, opt-in job/step.
- **major** — breaks workflow contract: removing/renaming input or secret, adding *required* input, changing default callers must react to, requiring new permissions.

Rule of thumb: if caller's shim could keep working untouched → patch/minor; if not → major. Unsure → prefer larger bump.

### How a merge reaches `tag-release.yml` - read before touching either file

`tag-release.yml` triggers on `push` to `main` and nothing else. Every merge in this repo is done by hand (squash), which raises a real `push`, so every merge is tagged. Nothing in this repo reviews or merges PRs automatically: review runs locally against the working diff before the push.

Consequences a change here is most likely to get wrong:

- **A `uses:` job validates inputs against the PINNED ref, not the PR.** So a
  PR adding an input to a reusable workflow *and* passing it from this repo's
  own self-calls (`release-extension.yml`'s three internal `uses:`) in one
  commit fails `Invalid input, <name> is not defined in the referenced
  workflow`: `startup_failure`. Split it: ship the input, let `tag-release.yml`
  move the major tag, then add the caller.
  Within one major that lag self-heals at the next tag. ACROSS a major it does
  not: `tag-release.yml` re-points only the CURRENT major, so the v7 cut froze
  `v6` at v6.2.4 (6c15ff7) exactly as the v6 cut froze `v5` and the v5 cut froze
  `v4` at v4.14.2. This repo's own pins were repointed by hand once each new
  major existed (#43, #56). A pin left behind on a frozen major is the one case
  where the rest of this file describes behaviour the repo is not actually
  getting: check the pins first when something here does not match what you
  observe.

- **`#major` behaves asymmetrically by range.** On a real push range, a
  `#major` not on the head subject is a hard `exit 1`. With no usable push
  range (a first push, a force-push that orphaned `before`, a re-run after a
  history rewrite) the scan spans last-release-tag..HEAD and re-reads every
  unreleased commit on every run, so a refusal there would wedge the workflow
  permanently; it warns and downgrades instead.

## Runners — hosted by default, ARC only for the cluster

**Since v8 every `runner` input defaults to `ubuntu-latest`, and `arc_runner_defaults()` in `scripts/check-workflows.py` asserts it** — including the exception list, in both directions, so a new workflow copied from an existing input block cannot reintroduce an `arc-*` default in silence, and a cluster workflow cannot gain a default of any kind (a hosted one costs nothing until a deploy fails; a pool one queues forever in every repo but the pool's own). The two exceptions are `deploy-k8s.yml` and `deploy-helm.yml`, which since v9 take no `runner` default and declare it `required: true` (#59), and always will need a pool: they authenticate as the runner pod's own mounted ServiceAccount token, and `k3s.itguys.ro` resolves to `192.168.1.5`, an RFC1918 address no GitHub-hosted runner can route to. Neither is a thing a flag turns off. The ARC scale sets in `ITGuys-RO/k3s-cluster` stay deployed for those two workflows; `runner-image/` and `runner-image.yml` stay with them, because those deploy jobs still need the image's baked `kubectl` and `envsubst`. **A default is not a migration**, so do not read that as "nothing else runs on a pool": a caller passing `runner:` explicitly keeps it, and a caller that passes `runner:` explicitly keeps its pool. This repo's own self-pins were the first callers swept, the moment v8.0.0 existed: `release-extension.yml`'s three internal calls moved to `@v8` and dropped their `arc-df-shared-workflows`, and `release-extension.yml` gained `package-manager-cache` and `cache-dependency-path` passthroughs it never had — without them an extension caller dropping its `runner:` got a hosted runner with an empty store every job and no way to turn the cache on, since v7's `node-test.yml` defaults that input **false**. None of it could be done earlier: a `uses:` job validates its inputs against the PINNED ref, so `@v8` is a `startup_failure` until the tag exists, and the passthroughs would have been undeclared inputs on v7. Check the pins before believing any sentence here describes what is actually running.

**Sweeping a caller: repoint the pin and drop its `runner:` in the same commit, never separately.** Dropping the pin while the `uses:` still says `@v7` hands the job v7's default, `arc-df-shared-workflows` — a scale set that exists for THIS repo and not for the caller's account — so the job queues forever with `runner_name: ""` and no error anywhere. Measured 2026-09-22 on `dustfeather/social-update`: in one run the two `node-test.yml@hosted-runners` jobs finished green on `ubuntu-latest` while the two still-`@v7` jobs that had only lost their pin sat queued until the run was cancelled. It reads as a busy pool, not as a misconfiguration, which is why it is worth stating.

**The fleet was swept on 2026-09-22** — 20 caller repos, pushed straight to each default branch: 86 pins moved to `@v8`, 81 `runner: arc-*` inputs dropped, 38 caller-native `runs-on: arc-*` rewritten, and 44 `with:` blocks deleted once their last input went (a `with:` mapping to null is valid YAML and silent in actionlint, and fails the run with zero jobs and no annotation). What still carries an `arc-*` label is exactly the cluster set: every `deploy-k8s.yml` / `deploy-helm.yml` call in `ITGuys-RO/nextcloud`, `dustfeather/dosar-rapid.ro` and `dustfeather/social-update`, plus three caller-NATIVE nextcloud jobs (`deploy.yml`: `secrets`, `validate-manifests`; `pr-checks.yml`: `validate`). Those three native jobs are not borderline: `nextcloud` `pr-checks.yml`s `validate` runs `helm template | kubectl apply --dry-run=server` plus `kubectl diff`, and `deploy.yml`s `validate-manifests` does the same — server dry-run sends the object to the apiserver for admission and validation, so nothing is persisted but the request is real. (An earlier revision of this paragraph called them `--dry-run=client`; that was wrong, and the client case would still have qualified, since a client dry-run GETs the resource and the namespace anyway.) The one thing the sweep could not predict was the undeclared-dependency class below: `dustfeather/dustfeather` went red on its first hosted run with `claude: command not found` (exit 127, run 35731415970) because the ARC image `npm install -g @anthropic-ai/claude-code` and no workflow ever named it.

**The pools the sweep orphaned were uninstalled on 2026-09-22**, so an `arc-*` label is no longer a thing a caller can reach for. 18 of the 21 scale sets went (`ITGuys-RO/k3s-cluster@7229fd1`); what is left is one pool per repo that still deploys into the cluster — `arc-df-dosar-rapid`, `arc-df-social-update`, `arc-itguys-ro-nextcloud`. Writing `runner: arc-<anything-else>` now queues the job forever with `runner_name: ""` and no annotation, which is the same silent shape as a caller that kept its `runner:` while moving to `@v8`. Since v9 `deploy-k8s.yml` and `deploy-helm.yml` declare `runner` as `required: true` with **no default** (#59). Their v8 default, `arc-df-shared-workflows`, was one of the deleted names and could never have reached a caller anyway, since that pool was bound to THIS repo; a required input turns the omission into a `startup_failure` naming the input instead of a job queued forever. `arc_runner_defaults()` asserts the shape: any default on a cluster workflow is a finding.

**A self-hosted runner image is an undeclared dependency, and this repo has been bitten by it.** Anything installed by `runner-image/Dockerfile` is on PATH for every job on an ARC pool without being named anywhere in the workflow, so a workflow READS as self-contained while it is not. Before pointing anything else at `ubuntu-latest`, grep the Dockerfile for what that workflow consumes, and grep the whole workflow file for the tool's name, not just its `run:` blocks, because the reference may live inside a string handed to an action (a `settings:` JSON, a `with:` value, an `--mcp-config`). How loud the failure is depends on who calls the tool: a `run:` step gives you `command not found`, while an agent hook or an MCP server named in a JSON string fails once per invocation inside a subsystem whose errors read as "the agent regressed", and the job stays green. When a workflow installs a tool the image also bakes, its version is a **second copy**: assert the agreement statically rather than leave a comment asking the next reader to remember.

`package-manager-cache` in `node-test.yml` defaults **true** since v8, and `deploy-cloudflare.yml` passes `cache:` unconditionally, for the same reason inverted: a hosted runner starts from an empty store every job. Both defaulted off while every caller was on a pool mounting a persistent node-local store, where the restore round-trips that store through the throttled in-cluster cache service for nothing. A caller still pinned to an ARC pool should pass `package-manager-cache: false` — the two defaults are opposite for opposite reasons, and neither is the wrong one.

## Conventions

- Inputs added to reusable workflow MUST default to value preserving prior behavior. **A major bump is the one place that may be traded away, and then only for a default the major is cut FOR.** v8 spent it exactly twice: `node-test.yml`'s `package-manager-cache` flipped false→true, and `deploy-cloudflare.yml` gained the same input at `true` where it previously did not cache at all. Both are behaviour changes to a caller that passes nothing, both are the point of the runner move (a hosted runner starts from an empty store every job, which inverts the reasoning that made them off), and both ship with an opt-out a pool-pinned caller can pass. v9 spent it on `timeout-minutes` (#62): every callable workflow gained the input at 360 in v8.2.0, then v9 lowered each default to a few times the slowest successful run measured across callers (node-test 60, deploy-cloudflare 30, the rest in each input's description). A caller with a genuinely long job raises it. Anything that cannot be argued that way still defaults to the old behaviour, major or not.
- Every workflow declares explicit top-level `permissions:` block; jobs needing more declare own. CodeQL flags missing — hard error, not warning.
- Reusable workflows run in **caller's** context with caller's secrets. `secrets: inherit` works for same-owner callers; cross-owner (`ITGuys-RO/*`) MUST pass secrets explicitly — `inherit` does not reliably carry org-level "selected"-visibility secrets across owner boundary.
