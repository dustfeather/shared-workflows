# CLAUDE.md

Library of reusable GitHub Actions workflows (`workflow_call`) in `.github/workflows/`, consumed by every other repo under this account via `uses: dustfeather/shared-workflows/.github/workflows/<name>.yml@v8`. No app code. A merged change ships to every caller on next run — treat blast radius accordingly. Four workflows are NOT callable — this repo's own automation: `tag-release.yml` (cuts the version tag), `pr-merge.yml` (lands a PR the review agent approved), `pr-checks.yml` (runs the review) and `guard-tests.yml` (runs the guard suite below, plus actionlint over every workflow).

## Verifying changes

**Touching the bump-token guard in `merge-on-approval.yml` — the `run:` block between the `# guard-slice-begin` and `# guard-slice-end` markers — run `bash tests/guard/all.sh` before pushing.** Describe the region by those markers and nothing else. It used to be described here, and anchored in `tests/guard/extract.sh`, by the `if [ "$method" = "--squash" ]` line; that made the condition the one line the suite could not mutate, because mutating it deleted the anchor and the slice silently matched ~290 lines further down. The markers exist to end that, and `extract.sh` now refuses rather than guessing when they are absent — so moving or rewriting that condition is fine, and dropping the markers is not. It is the local check for that block and it is not optional: the guard sits in the one path with no retry, where a nonzero exit after the merge costs the release tag outright. The pre-push hook runs it, so it is enforced rather than merely declared — it used to say this while `.githooks/pre-push` ran only `check-workflows.py`, which made the one check called mandatory the one nothing local gated. The suite RE-EXTRACTS the block verbatim from the shipped YAML on every run, so it always tests the bytes that ship and cannot drift from an edit — but equally, an edit that breaks it fails immediately rather than at merge time. `guard-tests.yml` runs the same script on every push and pull request, and since 2026-09-14 its `guard` job is the **one required status check on `main`**, so a red suite blocks the bot merge (which runs as `github-actions[bot]`, not an admin) instead of merely reporting. `enforce_admins` is deliberately `false` — an owner's direct push still bypasses it, which is what keeps the `pr-checks.yml` remedy below available. No `required_pull_request_reviews`: protection says nothing about WHO may approve (that is `pr-merge.yml`'s `if:`) and there is no `dismiss_stale_reviews`, so `match-head-commit` stays load-bearing.

Two suites, because a stubbed `gh` can only pattern-match argv and is therefore blind to a program passed INSIDE argv: `tests/guard/run.sh` covers the shell, `tests/guard/jqtest.sh` runs the `--jq` program against real jq. Assert on the recorded `gh pr merge` argv (the `argv:` prefix), not on the guard's own log lines — an `echo` survives deleting the flag it describes.

**Touching the pnpm-version guard — the `run:` block between the `# pnpm-guard-slice-begin` and `# pnpm-guard-slice-end` markers, shipped in `node-test.yml`, `deploy-cloudflare.yml` and `release-extension.yml` — run `bash tests/pnpm-guard/run.sh` before pushing.** Same marker discipline as above and for the same reason: describe the region by the markers and nothing else, and `tests/pnpm-guard/extract.sh` refuses rather than guessing when they are absent. Two things are specific to this one. The block is duplicated across workflows, and the extractor **derives** the set rather than holding a list: every `.github/workflows/*.yml` carrying the markers, asserted equal to the set calling `pnpm/action-setup`, in both directions — a caller with no slice is a guard nobody tests, and a slice in a workflow that never calls the action is a guard that cannot fire. Never replace that with a hand-written list. A list is what lets someone add a fourth workflow by copying the pnpm block, set its `PNPM_BOOTSTRAP_VERSION` literal correctly so `check-workflows.py` passes, break the copied guard, and ship green — the extractor would never read the file. It then refuses unless the copies are **byte-identical**: the suite exercises one on behalf of all, so drift between them is a failure, not a diff. And the branch worth protecting is the warn path: it exits 0 on a value the workflow itself calls wrong, so an inverted `-z` or a typo that stops the guard firing is green in every caller until it reaches a pool exporting `pnpm_config_store_dir` — the same "first run passes, a later one dies" shape the guard exists to prevent. Assert the annotation alongside the exit status, never the status alone. The pre-push hook and the `guard` job both run it; in CI it is its own step rather than part of `tests/guard/all.sh`, because a failure here means the pnpm branch logic moved and should not arrive wearing the bump-token guard's name.

**Raising the pnpm pin is one commit, never two.** The `pnpm-version` default, the `pnpm/action-setup@<sha>` pin and that SHA's committed bootstrap lockfiles are a three-way agreement, and `scripts/check-workflows.py` asserts all three (the lockfile leg under `CHECK_PNPM_BOOTSTRAP=1`, which the hook and the `guard` job both set). An unreachable lockfile is a **hard** failure by default; `PNPM_BOOTSTRAP_SOFT=1` downgrades it to a note and **only the pre-push hook may set it**, so that an offline push is not blocked by a check that never disagreed. The switch is an opt-in to silence rather than an opt-in to strictness on purpose: it used to read ambient `CI`, which made the required check's strictness depend on a variable nothing declared, so a tidy-up of an `env:` block could turn it into a green no-op. `check-workflows.py` now asserts the `guard-tests.yml` step sets `CHECK_PNPM_BOOTSTRAP=1` and does **not** set `PNPM_BOOTSTRAP_SOFT`, reading the parsed `env:` maps rather than the file text — a text scan matches the comment explaining why the variable is absent, and "fix" it by deleting the explanation. The action never reads the runner image's pnpm: `runSelfInstaller()` wipes its dest dir, installs from its own committed lockfile and then runs `pnpm self-update <input>` unconditionally — so the default matters only in that it must equal what the pinned SHA bootstraps, which makes that self-update a no-op. Any other value installs pnpm THROUGH pnpm into the shared store and kills every job after the first. Move the SHA, the default and the `PNPM_BOOTSTRAP_VERSION` literal in all three guards together, in the same commit.

**Touching the cache-glob block — the `run:` block between the `# cachedeps-slice-begin` and `# cachedeps-slice-end` markers, shipped in `node-test.yml` and `deploy-cloudflare.yml` — run `bash tests/cachedeps/run.sh` before pushing.** Same marker discipline as the two guards above, and `tests/cachedeps/extract.sh` refuses rather than guessing when the markers are absent. What makes this block worth a suite is that its output is `actions/setup-node`'s `cache-dependency-path`, and with `cache` set setup-node **fails the step** rather than skipping when nothing in that list resolves — on `deploy-cloudflare.yml` that is the deploy path, and a reusable workflow cannot be run from a local checkout, so extraction is the only way to exercise it before it reaches every caller. Two things are specific to it. The copies are NOT byte-identical — one reads `WORKING_DIR`, the other `INSTALL` — so the pnpm guard's identity assertion does not apply; instead every case runs against both slices and asserts they agree, which catches drift without demanding a sameness the files cannot have. Each slice is given **only its own** directory variable, read from the shipped `env:` block by `extract.sh --env-keys` — never both. Exporting both is what would make the copies agree on a mistake rather than catch it: the way a third copy gets made is by pasting an existing slice, and a pasted `${INSTALL:-.}` inside `node-test.yml` does not trip `set -u`, so it silently reads `.` for every `working-dir` and emits root-only globs. That reaches only callers whose lockfile sits under `working-dir` — the default shape stays green, which is the same "first run passes, a later one dies" pattern the pnpm guard exists for. The suite also refuses when a slice never references the variable its own workflow declares. And the set of copies is derived, not listed: the marked files are asserted equal to the files carrying an `id: cachedeps` step, anchored so that prose merely naming the id does not count (`guard-tests.yml` carries exactly that in a comment). Half the suite asserts an ABSENCE — no `*lock*` glob, nothing that `Cargo.lock` could satisfy — because the too-broad glob passes every shape assertion and still keys the node cache off a Rust file, and because a repo with only a `Cargo.lock` at the root would satisfy setup-node's lookup instead of failing loudly.

Everything else: the checks are a YAML parse (`python3 -c "import yaml; yaml.safe_load(...)"`) plus `scripts/check-workflows.py`, and `actionlint` over every workflow. `check-workflows.py` is no longer local-only — it runs in CI as a step of the `guard` job, which is the one required status check on `main`, so its findings now block a merge instead of only a push. Treat a new assertion in it as changing what that gate enforces fleet-wide, and give it a fixture case in `tests/check-workflows/run.py` rather than relying on the clean tree passing — that proves the happy path and nothing else, and a regex here has already shipped broken twice (one double-escaped and matched nothing, one matched prose instead of `uses:` lines, both green). The fixtures are offline: every case reaching the network stubs `fetch_json`, and the ones that do not stub it never set `CHECK_PNPM_BOOTSTRAP`, so no case can hit api.github.com by accident. The pre-push hook runs the contract checks, the bump-token guard suite, the pnpm-version guard suite, the cache-glob suite, the workflow-check fixtures and the lint as six independent checks, each probing for its own dependencies (PyYAML for the first, `jq` for the second, `python3` alone for the third and the fourth — both guards under test are pure shell, but each `extract.sh` slices its block out with a python3 heredoc — PyYAML again for the fifth, and `actionlint` AND `shellcheck` for the sixth) and skipping only itself — a single missing dependency must not take the others down with it. The lint probes for `shellcheck` separately because actionlint drops every shell check when it cannot find that binary and still exits 0, so a clean run without it would mean nothing. **The same lint runs in CI as the last step of `guard-tests.yml`'s `guard` job** — which runs, in order, `tests/guard/all.sh`, `tests/pnpm-guard/run.sh`, `tests/cachedeps/run.sh`, `tests/check-workflows/run.py`, `check-workflows.py` under `CHECK_PNPM_BOOTSTRAP=1`, then actionlint — deliberately that job rather than a new one, because `guard` is the one required status check on `main`, so a step there is enforced the moment it lands while a new job would gate nothing until branch protection is edited. CI pins actionlint by version and sha256; a local binary of another version shows up as a CI-only finding, and the fix is to bump the local binary, never to suppress the finding. A false positive is silenced with a scoped `# shellcheck disable=SCxxxx` comment carrying a one-line reason — the ones that ship today cover three shapes (literal `${NPM_TOKEN}` in an .npmrc line, GraphQL `$variables` inside single quotes, and the deliberate word split on `$del $match` in the merge argv), and each is load-bearing: "fixing" it by quoting would break the thing it documents. Reusable workflows cannot be invoked from a local checkout — `uses:` resolves through GitHub. Real e2e test: push to feature branch, point one caller at it (`@feature/<name>`) before tagging.

## Versioning — pick bump by caller impact

`tag-release.yml` auto-tags every push to `main`: default bumps **patch** (wraps at 100 → minor; minor uncapped), re-points the floating major tag (currently `v7`). **major never bumped automatically.** Larger bump: put `#minor` or `#major` **in the PR title** when it lands through a PR, **on the commit subject** when pushed straight to `main` (largest wins). Match is fixed-string over the **subject** of **every commit in the push**, not just HEAD — one push fires one run, so a HEAD-only scan would drop a token from an earlier commit in a batch. Bodies are excluded on purpose: prose *discussing* a bump matched itself and cut a spurious minor. Don't write tokens verbatim unless you mean them — **in a PR title least of all**, since that text is now always the landing subject, so prose merely *naming* a token cuts that release. This is the same failure the body exclusion exists to stop, on the one channel where no exclusion is possible.

**PR title, since 2026-09-14**, when `pr-merge.yml` moved to `merge-method: squash` so main's history verifies (a rebase merge is replayed server-side and arrives unsigned; GitHub signs a squash commit with its web-flow key). A squash lands one commit, and `merge-on-approval.yml` passes `--subject "<the PR title>"` so that commit's subject is the PR title by construction. The flag is what makes the rule single-valued: without it the subject comes from the repo's `squash_merge_commit_title`, and GitHub's default `COMMIT_OR_PR_TITLE` uses the commit's own subject on a single-commit PR, switching to the PR title only from two commits up — so the advice would depend on a per-repo setting and on the commit count. The guard refuses a merge when a bump asked for anywhere is missing from the PR title; the fix it names is editing the title, which needs no new commit and so does not drop the approving review. A direct push to `main` is unaffected — nothing replays it.

**The title stops being editable earlier than you think, on BOTH modes.** The freeze point is the guard's own `pr_title` read at the top of its step: that value is baked into `squash_subject` and passed as `--subject`, and nothing re-reads the title afterwards. An edit after that changes nothing on `direct` either — `direct` only gives a shorter window, because its merge follows within seconds. `merge-on-approval.yml` defaults to `auto`, and `enablePullRequestAutoMerge` stores the subject: GraphQL's `AutoMergeRequest` carries `commitHeadline` next to `enabledAt`, so GitHub keeps what `gh` sent when auto-merge was enabled and does not re-read the title when it later merges. **Measured, not inferred** (2026-09-14, throwaway repo): auto-merge enabled with a subject distinct from the title stored that subject in `commitHeadline`; the title was then edited and `commitHeadline` did not move; the landed squash commit carried the stored subject, not the edited title. Editing the title after that run changes nothing about the release it cuts — the remedy is a re-run, which needs a fresh approving review or a manual dispatch. The guard says which of the two situations you are in, and it says so on every squash merge. The `::warning::` annotation, though, is raised only when the PR title actually carries a bump token — the case where an incidental token cuts a release nobody asked for. With no token in the title the same text is logged plainly, because `auto` is the default and a yellow annotation on every merge in every caller repo is how an annotation stops being read. The gate is on the RANK, not the mode: `direct` annotates on the same condition, since an incidental token cuts the unasked-for release there too, only sooner — and `direct` is what this repo's own `pr-merge.yml` passes, which makes it the last place to exempt. The two modes differ in WORDING, not in whether they annotate. This repo's own `pr-merge.yml` passes `mode: direct` (it has to merge synchronously, see below), so here the window between the read and the merge is seconds rather than open-ended — short, not live.

**A PR with more than 250 commits is refused, not merged.** Caller-visible and new in v6, on the DEFAULT settings (`merge-method: squash`, `mode: auto`), so a caller that overrides neither is affected. To decide the bump the guard has to read every commit subject on the PR, and the pull-request commits endpoint stops at 250 however far it is paginated — a bump token on commit 251 would be silently invisible, which is the exact failure this guard exists to prevent. It therefore compares the subjects it read against the PR's own `.commits` total (uncapped: measured at 780 on a PR whose listing returns 250) and refuses on any shortfall rather than deciding a release from a partial list. **Remedy: merge that PR by hand, or split it.** The refusal names one of three causes and cannot see a fourth: the head SHRANK between the two reads (a force-push or base rebase), the declared count is past the 250 cap so the list was most likely truncated, or the declared count is within the cap so what is left is a push landing between the commit read and the count read. A failed PAGE is deliberately NOT among them: `pr_subjects` is assigned from a command substitution, so under the step's `set -euo pipefail` a nonzero `gh api` kills the step before the comparison is reached. Do not restore that claim here -- the guard's own comment argues the point at length, and this file is the spec the next agent reads.

- **patch** — bug fix, doc/log/comment tweak, internal refactor, bumping action used inside workflow with no interface change.
- **minor** — backwards-compatible feature: new *optional* input (with default), new workflow, opt-in job/step.
- **major** — breaks workflow contract: removing/renaming input or secret, adding *required* input, changing default callers must react to, requiring new permissions.

Rule of thumb: if caller's shim could keep working untouched → patch/minor; if not → major. Unsure → prefer larger bump.

### How a merge reaches `tag-release.yml` — read before touching either file

`pr-merge.yml` lands a PR the review agent approved, merging with the default
`GITHUB_TOKEN`. GitHub creates **no workflow run from events raised by that
token**, so a bot merge fires no `push` — and that suppression belongs to the
token, not the trigger, so `pull_request: [closed]` is dead too. There is no
merge event to listen for. `tag-release.yml` therefore has a second trigger,
`workflow_run` on **`"PR merge on approval"` matched by NAME**: renaming
`pr-merge.yml`'s `name:` stops all tagging and is not an error.

Consequences a change here is most likely to get wrong:

- **`pr-merge.yml` must merge synchronously** (`mode: direct`). `--auto`
  returns before the merge, so the run completes — raising `workflow_run` —
  while `main` is still the pre-merge commit; tag-release then sees the head
  already tagged, exits clean, and the commit is stranded untagged for good.
- **`tag-release.yml`'s guard on `workflow_run.conclusion == 'success'` is
  the load-bearing one.** `types: [completed]` delivers every conclusion, and
  a run whose only job is filtered out concludes `skipped` (measured: runs
  34702777640, 34702294904) — the conclusion test is what drops it. The
  shim's own `if:` on state and draft duplicates what `merge-on-approval.yml`
  checks internally; keep it, because it stops pointless runs and keeps the
  intent next to the trigger, but do not mistake it for the thing preventing
  a `changes_requested` review from cutting a release.
- **A `uses:` job validates inputs against the PINNED ref, not the PR.** So a
  PR adding an input to a reusable workflow *and* passing it from this repo's
  own shim in one commit fails `Invalid input, <name> is not defined in the
  referenced workflow` — `startup_failure`, merge job never starts, PR cannot
  land itself. Merge it by hand, or split: ship the input, let `tag-release.yml`
  move the major tag, then add the caller.
  Within one major that lag self-heals at the next tag. ACROSS a major it does
  not: `tag-release.yml` re-points only the CURRENT major, so the v7 cut froze
  `v6` at v6.2.4 (6c15ff7) exactly as the v6 cut froze `v5` and the v5 cut froze
  `v4` at v4.14.2. **All five of this repo's own pins were repointed to `@v6` by
  hand once v6.0.0 existed (#43), and to `@v7` once v7.0.1 existed (#56)** — the
  two live self-calls plus the three usage comments — so its merges DO run the
  squash `--subject` and the bump-token guard described above, and this repo is
  not the one caller left behind on the major that shipped the pnpm-12 store
  poisoning. A
  pin left behind on a frozen major is the one case where the rest of this file
  describes behaviour the repo is not actually getting — check the pins first
  when something here does not match what you observe.
- **`pr-checks.yml` names ITSELF in its own `paths-ignore`.** A PR whose only
  changed file is `.github/workflows/pr-checks.yml` changes a non-empty set of
  files, every one of them excluded, so GitHub creates **no run object** — not a
  skipped run, absent. No run means no review; no review means no approval; and
  `pr-merge.yml` triggers on `pull_request_review`. So such a PR cannot land
  itself, nothing goes red, and it sits waiting for CI that will never be
  scheduled. **Push that file straight to `main`** — that is how the `@v4`→`@v5`
  pin bump shipped, and it is the only remedy. Bundling the edit with a change to
  another path looks like a second option and is not one: the run then exists, but
  `claude-code-action` rejects its OIDC exchange whenever the PR edits the
  workflow that triggered the run, then swallows the 401 and exits 0. So
  bundling trades "no run at all" for "a green run that reviewed nothing",
  which is strictly worse here — the first failure is visible, the second is
  not. Treat bundling as a failure mode, not a fallback.

- **Since 2026-09-22 the review job is gated to Dependabot**, here and in all 19
  other caller repos: `if: ... && github.event.pull_request.user.login ==
  'dependabot[bot]'`. Human- and agent-authored PRs are reviewed locally against
  the working diff before the push, which is where a finding is still free to
  act on. The Dependabot track stays in CI because nobody is at a terminal when
  Dependabot opens a PR, and because that review is what ends on an approve —
  the event `dependabot-auto-merge.yml` and `merge-on-approval.yml` wait for.
  Two consequences to hold onto: a human PR in this repo now gets **no approving
  review**, so `pr-merge.yml` never fires and you merge it yourself (a manual
  merge raises a real `push`, so `tag-release.yml` still tags it through its
  push trigger, not the `workflow_run` one); and the gate lives in each caller's
  shim rather than in `claude-code-review.yml`, because callers float on `@v8`
  and a behaviour flip there would reach the whole fleet with no repin — the one
  blast radius a policy change should not have.

- **`#major` behaves asymmetrically by path.** On a real push range, a
  `#major` not on the head subject is a hard `exit 1`. On the `workflow_run`
  path there is no push range, so the scan spans last-release-tag..HEAD and
  re-reads every unreleased commit on every run — a refusal there would wedge
  the workflow permanently, so it warns and downgrades instead.

## Runners — hosted by default, ARC only for the cluster

**Since v8 every `runner` input defaults to `ubuntu-latest`, and `arc_runner_defaults()` in `scripts/check-workflows.py` asserts it** — including the exception list, in both directions, so a new workflow copied from an existing input block cannot reintroduce an `arc-*` default in silence, and a cluster workflow cannot be tidied onto a hosted one (which costs nothing until a deploy fails). The two exceptions are `deploy-k8s.yml` and `deploy-helm.yml`, which keep `arc-df-shared-workflows` and always will: they authenticate as the runner pod's own mounted ServiceAccount token, and `k3s.itguys.ro` resolves to `192.168.1.5`, an RFC1918 address no GitHub-hosted runner can route to. Neither is a thing a flag turns off. The ARC scale sets in `ITGuys-RO/k3s-cluster` stay deployed for those two workflows; `runner-image/` and `runner-image.yml` stay with them, because those deploy jobs still need the image's baked `kubectl` and `envsubst`. **A default is not a migration**, so do not read that as "nothing else runs on a pool": a caller passing `runner:` explicitly keeps it, and a caller that passes `runner:` explicitly keeps its pool. This repo's own five self-pins were the first callers swept, the moment v8.0.0 existed: `pr-merge.yml` and `release-extension.yml`'s three internal calls moved to `@v8` and dropped their `arc-df-shared-workflows`, and `release-extension.yml` gained `package-manager-cache` and `cache-dependency-path` passthroughs it never had — without them an extension caller dropping its `runner:` got a hosted runner with an empty store every job and no way to turn the cache on, since v7's `node-test.yml` defaults that input **false**. None of it could be done earlier: a `uses:` job validates its inputs against the PINNED ref, so `@v8` is a `startup_failure` until the tag exists, and the passthroughs would have been undeclared inputs on v7. `pr-checks.yml` is the exception that has to stay visible — it names itself in its own `paths-ignore`, so it can only be repointed by a direct push to `main`. Check the pins before believing any sentence here describes what is actually running.

**Sweeping a caller: repoint the pin and drop its `runner:` in the same commit, never separately.** Dropping the pin while the `uses:` still says `@v7` hands the job v7's default, `arc-df-shared-workflows` — a scale set that exists for THIS repo and not for the caller's account — so the job queues forever with `runner_name: ""` and no error anywhere. Measured 2026-09-22 on `dustfeather/social-update`: in one run the two `node-test.yml@hosted-runners` jobs finished green on `ubuntu-latest` while the two still-`@v7` jobs that had only lost their pin sat queued until the run was cancelled. It reads as a busy pool, not as a misconfiguration, which is why it is worth stating.

**The fleet was swept on 2026-09-22** — 20 caller repos, pushed straight to each default branch: 86 pins moved to `@v8`, 81 `runner: arc-*` inputs dropped, 38 caller-native `runs-on: arc-*` rewritten, and 44 `with:` blocks deleted once their last input went (a `with:` mapping to null is valid YAML and silent in actionlint, and fails the run with zero jobs and no annotation). What still carries an `arc-*` label is exactly the cluster set: every `deploy-k8s.yml` / `deploy-helm.yml` call in `ITGuys-RO/nextcloud`, `dustfeather/dosar-rapid.ro` and `dustfeather/social-update`, plus three caller-NATIVE nextcloud jobs (`deploy.yml`: `secrets`, `validate-manifests`; `pr-checks.yml`: `validate`). Those three native jobs are not borderline: `nextcloud` `pr-checks.yml`s `validate` runs `helm template | kubectl apply --dry-run=server` plus `kubectl diff`, and `deploy.yml`s `validate-manifests` does the same — server dry-run sends the object to the apiserver for admission and validation, so nothing is persisted but the request is real. (An earlier revision of this paragraph called them `--dry-run=client`; that was wrong, and the client case would still have qualified, since a client dry-run GETs the resource and the namespace anyway.) The one thing the sweep could not predict was the undeclared-dependency class below: `dustfeather/dustfeather` went red on its first hosted run with `claude: command not found` (exit 127, run 35731415970) because the ARC image `npm install -g @anthropic-ai/claude-code` and no workflow ever named it.

**The pools the sweep orphaned were uninstalled on 2026-09-22**, so an `arc-*` label is no longer a thing a caller can reach for. 18 of the 21 scale sets went (`ITGuys-RO/k3s-cluster@7229fd1`); what is left is one pool per repo that still deploys into the cluster — `arc-df-dosar-rapid`, `arc-df-social-update`, `arc-itguys-ro-nextcloud`. Writing `runner: arc-<anything-else>` now queues the job forever with `runner_name: ""` and no annotation, which is the same silent shape as a caller that kept its `runner:` while moving to `@v8`. The `runner` default on `deploy-k8s.yml` and `deploy-helm.yml` is one of the deleted names, `arc-df-shared-workflows`: harmless, because that pool was bound to THIS repo and no caller could ever have reached it, but it is a default that lies — issue #59 proposes making the input required in the next major rather than guessing a label for a job that has no hosted equivalent.

**A self-hosted runner image is an undeclared dependency, and this repo has been bitten by it.** Anything installed by `runner-image/Dockerfile` is on PATH for every job on an ARC pool without being named anywhere in the workflow, so a workflow READS as self-contained while it is not. Before pointing anything else at `ubuntu-latest`, grep the Dockerfile for what that workflow consumes — and grep the whole workflow file for the tool's name, not just its `run:` blocks, because the reference may live inside a string handed to an action (a `settings:` JSON, a `with:` value, an `--mcp-config`). How loud the failure is depends on who calls the tool: a `run:` step gives you `command not found`, while an agent hook or an MCP server named in a JSON string fails once per invocation inside a subsystem whose errors read as "the agent regressed", and the job stays green. The v8 move paid this twice in `claude-code-review.yml`. `path_to_bun_executable` / `path_to_claude_code_executable` pointed at `/usr/local/bin/{bun,claude}` — a hard failure on a hosted runner, so they were dropped and the action installs its own. `code-review-graph` came only from the image and is named in an `--mcp-config` string rather than any `run:` block, so its absence was silent; it is now an install-if-missing step guarded by `command -v`, pinning a version that is a **second copy** of the Dockerfile's `CRG_VERSION`. Nothing at runtime errors when those two drift — the pools and the hosted runners just build the graph with different parsers, surfacing as "the review got worse on one runner type" — so the agreement is asserted statically instead, by `runner_image_pin_drift()` in `scripts/check-workflows.py`, which runs inside the `guard` job and is fixtured in `tests/check-workflows/run.py`. Same treatment as the pnpm three-way agreement, for the same reason: a comment asking the next reader to remember is what a derived check exists to replace.

The same audit turned up the inverse case, and it is the one worth remembering: the `pr-review-toolkit` plugin is also baked into the image's `~/.claude`, and installing it here would have been waste. The prompt tells the agent to do the whole review itself, and `--allowed-tools` grants no `Task` and no `Skill`, so the plugin's agents are unreachable in this job whether or not they are installed. **Price what a baked tool actually buys, per consumer, before writing the install step** — a dependency can be load-bearing in one workflow and inert in another, and the inert case is easy to miss precisely because nothing ever errors. Writing that step is also harder than it looks to do honestly: guarding it with `command -v claude || exit 0` would have been a permanent green no-op, since nothing puts `claude` on PATH before the action runs. A guard is only a guard when something could plausibly have satisfied it.

`continue-on-error` on the `code-review-graph` step is a deliberate exception, not the pattern: the agent prompt carries an explicit `gh pr diff` fallback, so a review without the graph is degraded rather than wrong. A step with no fallback does not get that treatment — swallowing its failure would restore the exact silence this section is about.

`package-manager-cache` in `node-test.yml` defaults **true** since v8, and `deploy-cloudflare.yml` passes `cache:` unconditionally, for the same reason inverted: a hosted runner starts from an empty store every job. Both defaulted off while every caller was on a pool mounting a persistent node-local store, where the restore round-trips that store through the throttled in-cluster cache service for nothing. A caller still pinned to an ARC pool should pass `package-manager-cache: false` — the two defaults are opposite for opposite reasons, and neither is the wrong one.

## Conventions

- Inputs added to reusable workflow MUST default to value preserving prior behavior. **A major bump is the one place that may be traded away, and then only for a default the major is cut FOR.** v8 spent it exactly twice: `node-test.yml`'s `package-manager-cache` flipped false→true, and `deploy-cloudflare.yml` gained the same input at `true` where it previously did not cache at all. Both are behaviour changes to a caller that passes nothing, both are the point of the runner move (a hosted runner starts from an empty store every job, which inverts the reasoning that made them off), and both ship with an opt-out a pool-pinned caller can pass. Anything that cannot be argued that way still defaults to the old behaviour, major or not.
- Every workflow declares explicit top-level `permissions:` block; jobs needing more declare own. CodeQL flags missing — hard error, not warning.
- Reusable workflows run in **caller's** context with caller's secrets. `secrets: inherit` works for same-owner callers; cross-owner (`ITGuys-RO/*`) MUST pass secrets explicitly — `inherit` does not reliably carry org-level "selected"-visibility secrets across owner boundary.

## Code exploration

Plain `Grep`/`Glob`/`Read` are the tools here. 18 YAML workflows, no call graph — a knowledge graph earns nothing on this repo.

`code-review-graph` is **CI-only**: `claude-code-review.yml` installs it (pinned, install-if-missing), builds the graph and serves it over MCP to the review agent. It used to come only from the `actions-runner-claude` ARC image; since v8 that workflow defaults to a hosted runner and declares the dependency itself. It is not installed locally and no session here can call those tools. Any `.code-review-graph/` dir you find in a checkout is a stale leftover (gitignored) — delete it.

The local equivalent is the `graphify` CLI (pipx `graphifyy`, `graphify-out/` built in the app repos). Not wired as an MCP server; reach for it via the `graphify` skill, and only in a repo with real code to trace.
